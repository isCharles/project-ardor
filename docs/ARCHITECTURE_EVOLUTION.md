# Ardor 整体架构演进规划

日期：2026-10-18。状态：已纳入整体重构目标的架构基线；各阶段以实际交付与验收为准，本文件不代替原生 Goal。

研究基线：`35cfb39`（v0.6.2 发布准备）；重构起点包含 `5f3d505` 的已合并修复。本文件描述目标架构，不表示目标已实现。当前合同与分阶段验收边界见 [DOMAIN_CONTRACTS.md](DOMAIN_CONTRACTS.md)，原生 Goal 负责推进状态，不另建 Goal 文档。

## 1. 执行结论

**Ardor 应从“很多 AI 功能页的集合”，演进为“围绕求职与能力准备的个人工作系统”。目前值得做领域重构，但没有证据支持推倒重写。**

问题不只在名字。业务对象、操作、资料、统计视图和技术后台处于同一层，身份、来源、状态及扩展入口没有贯彻统一模型。若只合并菜单，后续仍会反复出现新的并列模块。

目标是同时稳定五件事：

1. 产品主线：用户知道事情在哪里发生、下一步去哪。
2. 数据归属：每种事实只有一个负责其生命周期的业务边界。
3. 执行合同：手动界面、Agent、后台任务使用同一套业务规则。
4. 扩展方式：新能力接入既有边界，不要求修改一串中央分支。
5. 演进纪律：保留用户数据、历史、授权和客户端兼容，不靠一次性全库改名制造第二套系统。

推荐保持模块化单体、现有前后端技术栈、PostgreSQL 与 Redis。未来用户增加，首先扩展部署容量与任务执行能力；不是提前引入微服务、消息中间件或通用工作流引擎。

本方案承诺的是明确的演进约束，不承诺“永远无需重构”。未来需求变化不可预知；应让变化局限在少量边界内，并能迁移、回滚和验证。

## 2. 产品定位与长期边界

### 2.1 Ardor 负责什么

围绕一个持续的循环：**了解目标岗位与现状 → 投递与真实面试 → 发现准备缺口 → 学习、训练和复习 → 再次面试与调整。**

对话是一种操作方式，而不是全部产品。用户可以告诉 Ardor 去安排，也可以直接在界面查看、修正和删除。两条路径必须得到一致结果。

### 2.2 暂不把什么做成平台

不在本轮建设招聘方 ATS、自动海投平台、多人企业协作平台、任意 Agent 插件市场或通用教育 LMS。它们可能将来成立，但不能用未经验证的需求决定今天的数据结构。

保持必要扩展缝隙：资源有稳定身份与所有者，外部来源可追踪，应用接口不依赖具体客户端，异步工作可由独立执行进程承接。暂不建立空租户、空组织、空课程树或万能实体表。

## 3. 全产品信息架构与命名

主导航：**Ardor · 求职 · 学习 · 日程**。搜索、通知、账户、设置与管理端属于支撑入口。用户可以固定子功能快捷方式，但快捷方式不等于独立业务领域。

| 一级入口 | 内部组织 | 不应继续并列出现的旧概念 |
|---|---|---|
| Ardor | 对话、历史、工作记录、上下文引用 | 运行状态、审批与任务不再各自拼出另一套聊天记录 |
| 求职 / Job search | 总览、投递、面试、简历与岗位材料 | opportunities 不再作为对用户暴露的真实面试概念 |
| 学习 / Learning | 主题、训练、复习、补强进度、资料入口 | 模拟面试、回放、记忆卡、evidence 不再各自争夺一级领域身份 |
| 日程 / Calendar | 今天、安排、复习到期、手工及重复事项 | 不拥有其他领域的业务完成状态 |

术语必须先稳定，再动代码：

| 业务含义 | 产品用词 | 建议代码概念 |
|---|---|---|
| 公司—岗位的真实面试过程 | 面试 / Interviews | InterviewProcess |
| 真实面试的一轮 | 面试轮次 / Interview round | InterviewRound |
| 某轮转写、笔记与逐题整理 | 面试记录 / Interview notes；可保留“面经”俗称 | InterviewRecord、InterviewQuestion |
| AI 扮演面试官的练习 | 模拟面试 / Mock interview | MockInterviewSession |
| 再答一道旧题、接受变式测试 | 重新作答 / Retry；变式复测 | QuestionPracticeAttempt |
| 每日打招呼与简历投递数量、提醒 | 投递 / Applications | ApplicationActivity；两个每日计数各自独立 |
| 薄弱点与后续行动的汇总 | 补强进度 / Progress | ProgressQuery，非 Evidence 业务实体 |

**Interview 优先、明确表示真实面试；Mock Interview 必须带 Mock。** `opportunity` 可以将来用于确实存在的“潜在岗位机会”，但不能继续作为真实面试不得已的替代词。不能将当前面试流程直接宣称为完整岗位机会漏斗。

英文路由、Java 包名、表名、界面显示名不需要一次性一致改完；应通过兼容层逐步实现语义一致。

## 4. 目标领域地图与状态所有权

产品可以只有两条业务主线，但后端不应该只有两个巨型 Service。建议形成下列逻辑边界，物理包迁移按需进行。

| 边界 | 拥有的事实和状态 | 向外提供 | 不拥有 |
|---|---|---|---|
| 求职 Job search | 投递计数、真实面试流程、轮次、结果、面试记录与问题 | 面试详情、安排、问题来源、准备上下文 | 学习完成状态、模型调用、聊天状态 |
| 学习 Learning | 学习主题与计划、练习结果、模拟训练、记忆卡及复习 | 训练入口、到期项目、补强进度 | 真实面试结果、原始面试事实 |
| 资料 Materials | 简历版本、分析报告、知识资料、文件元数据、解析与检索来源 | 引用、检索、版本化分析结果 | 现实面试或学习状态 |
| 助手 Assistant | 会话、消息、运行、工作记录、操作提案、长期记忆 | 对话操作、工具装配、运行状态 | 各业务领域的核心校验和数据库写规则 |
| 日程 Scheduling | 手工事项、重复规则、领域安排的展示关联 | 日历查询、提醒与安排协调 | 用“日历打勾”替代训练评分或面试结果 |
| 平台 Platform | 身份、配置、模型/语音适配、任务机制、额度、通知、文件基础设施 | 稳定基础合同与观测信息 | 到处导入业务 Repository 的“万能公共层” |

依赖原则：界面和 Agent Tool 调用领域应用服务；领域应用服务控制授权、事务与状态；Repository 只属于其领域。跨领域通过有名字的应用接口合作，不通过“都在一个数据库里”任意访问对方 Repository。

查询聚合可有明确、受用户隔离的跨域只读投影；不能借此绕过写入归属。共享层只放真正通用的身份、时间、存储、任务等合同，不能成为业务杂物箱。

## 5. 核心模型与关系：先解决语义，再解决目录

### 5.1 真实面试

层级为：**InterviewProcess → InterviewRound → InterviewRecord → InterviewQuestion**。

- 流程拥有公司、岗位及整体结果；轮次拥有阶段、时间及该轮结果。
- 记录是该场事实材料的整理，不再要求用户重复填写已由父对象拥有的公司岗位信息。
- 一轮可能有转写、补记等多份来源，不预先限制为一轮一份文档。
- 历史面经只有流程关联时，允许“待归档到轮次”，不能猜成第一轮。
- 校验不仅是同一用户，还要保证轮次确属对应流程、记录确属对应轮次。
- 简历版本和 JD 可作为当时准备上下文关联；之后修改当前简历，不应重写旧面试的上下文事实。

### 5.2 投递

保留每天批量记数与催促机制，不要求每天投几十份的人创建几十条详细记录。当前计数不等于具体 Application 的集合，不作为可信的面试转化率分母。

如未来确实需要逐份投递，可新增独立 ApplicationRecord，并明确计数与明细的统计口径，避免把“记录一份明细”和“补记今天数量”重复计数。真实面试流程可关联该明细，也可手工创建，不强迫补齐不存在的投递历史。

### 5.3 学习与准备

学习拥有自己的生命周期。一个主题可来源于多道面试弱题，也可服务多个未来岗位；还可以完全自主开始。来源与目标应分开表达：

- 来源：为什么学，例如某道面试题、某份简历报告、用户主动提出。
- 目标上下文：为哪个岗位、哪场面试准备；可以没有。
- 学习版本：讲解及题目版本，不能重新生成后把旧答案挂到新题上。
- 学习结果：每次提交与评价保留，而不是只覆盖最后分数。

现有 `RECAP + sourceId` 同时表示整份面经或一道题，必须迁移成明确的来源类型。先做清楚的类型解析与授权，不引入任意实体都能互联的关系引擎。

### 5.4 训练与复习

统一发现入口和结果摘要，不统一所有状态机。模拟面试、单题重答、代码运行、课后练习、间隔复习各有自己的实体与生命周期。

可共享任务状态、计时、结果引用和来源合同；不能创建一张包含几十个可空字段的万能 TrainingSession。语音与文字首先是交互方式，不能再次长成互不关联的两套面试领域。

### 5.5 evidence 的去留

当前 evidence 页面在浏览器汇总面经、学习计划和记忆卡；没有独立后端业务实体，也没有完整读取重答评估结果。它不是应继续建设的独立领域。

**取消一级 evidence 身份，保留为“学习 → 补强进度”的只读查询能力，并在真实面试详情提供相应上下文视图。** 不新建 Evidence CRUD 或万能证据表。未来只有形成明确能力标准、测量方式与证据生命周期，才讨论独立评估模型。

练习次数、卡片自评、模型评分各有含义，不能直接合成一个号称证明能力的分数。

## 6. 资料、简历评分与知识检索

资料层分清三类东西：原始上传或外部来源、解析/切片等衍生数据、版本化 AI 分析。保存来源、版本、处理状态与资源归属；用户可定位分析依据，不用把聊天当成唯一档案。

简历评分的稳定性来自**规范化评分合同**，不是比较两份文件是否一样：

- 评分量表有版本、维度、权重、扣分条件与证据要求。
- 目标岗位及市场要求有来源与日期；量表更新不能悄悄改变旧报告含义。
- 可确定规则由代码计算；需要语义理解的证据提取按 schema 校验，并标出缺失或不确定。
- 优化建议按明确优先级给出“问题—证据—修改动作—预期收益”，不只输出泛泛评价。
- 保留输入版本、量表版本、模型/配置及评估结果；同版本、近似内容用样本做一致性回归。
- 不承诺 LLM 语义提取像数学函数一样绝对一致；温度低也不是可重复性的证明。需要区分规则分数与带不确定性的判断。

知识检索是资料能力，不是所有业务的数据库替身。删除源材料时，向量索引、引用和历史报告如何处理必须有明确策略；派生切片不能在源材料权限撤销后继续泄露正文。

## 7. Agent：理解、执行与事实分离

Agent 是协调者，不是业务数据库，也不能成为权限裁判。

一次工作至少分清：用户消息、AgentRun、模型阶段、工具调用、操作提案、业务结果与最终回复。关联可以共享稳定 ID，但不能把它们拼成同一种“消息字符串”。

### 7.1 消息与引导

用户发送后应先成为持久化消息，并获得确认，再开始异步运行。客户端重试使用稳定请求 ID；服务端幂等防止重复插入。刷新恢复根据持久化消息与运行状态重建，不复制上一轮缓存。

新消息可以对当前工作进行引导：明确保留原请求、新要求及已经发生的副作用。不能取消上一轮后只把最新一句交给模型，也不能在尚未停止的旧工具上并发执行冲突写入。应定义安全检查点、取消请求与终止确认，而不是把“停止”当成回滚。

运行结束、失败、取消均是明确终态；临时提示可消失，事实和操作记录不能消失。最终回复在工作记录之后；工作记录默认折叠，结果属于产生它的那一轮，不随每次回复重新挂到最下方。

### 7.2 工具、权限与建议

- 账号身份与资源隔离始终由服务器校验，用户隐藏一个菜单不等于撤销授权。
- 查询不应例行弹批准框。新增/修改在已有授权和明确意图内执行；主动建议可作为可接受/拒绝的提案呈现，不能把“建议”当作已完成事实。
- 删除必须展示真实目标、影响与范围，用户点击受鉴权界面确认后执行。确认绑定目标/版本和有效期，不让对话口令、引用材料或模型自述替代。
- 长期记忆可按用户已明确的策略自动维护，但需来源、可见性、编辑/删除和敏感信息保护；不能借记忆写入权限修改业务数据。
- 新增工具必须声明能力、输入/输出、授权、幂等、副作用和审计信息；模型适配不能绕过业务服务。
- 产品权限策略与本次领域重构分别验收。不得借改模块名静默扩大 scope，也不将新导航分类直接当成授权边界。

工具按领域装配。已有 `ToolCatalog`、模块授权等机制应先评估复用，不另建一套平行注册中心。文字说明帮助模型使用工具，服务器结构化规则保障执行正确；不能靠关键词包含“学习/修改”决定合法写入。

## 8. 模型、推理与语音的扩展边界

模型接入采用能力合同，而不是把供应商参数暴露到每个业务 Service：普通生成、结构化输出、工具调用、可用的推理摘要、流式输出、语音等能力按适配器声明和验证。

产品可以提供 Low/High/Max，但每个供应商的映射不同。记录实际采用的配置，不支持时明确降级或提示，不假装成功。禁止将整个请求耗时称为“纯思考时间”。

区分排队、上游连接、首个输出、可用推理输出、工具执行与等待确认。展示供应商明确提供且允许展示的推理文本或摘要；没有就展示状态，不伪造思考过程，不要求暴露隐藏推理。

失败应分类：DNS/连接、认证、限流、上游超时、格式校验、业务拒绝。流式与普通调用设置相应时限、心跳与取消传播；有心跳不代表模型有实质进展。自动重试结合幂等与费用，不能因重试重复删除、生成记录或扣费。

实时语音保持连接级身份与会话归属，明确 ASR、VAD、TTS、打断和重连责任。音频帧是实时数据，不能塞进持久化业务任务队列；转写、评分和面试结果按自己的保存策略落库。

## 9. 异步任务、事件与可靠性

长耗时 AI 分析通过持久化作业返回任务身份，页面可离开再回来。任务至少包含所有者、业务输入版本、状态、重试次数、租约、错误类别与结果引用。

已有各类队列不必一次性合表。先统一对外状态/结果查询合同和领域 Handler，再逐步收敛重复机制。任务内核不能继续随每个新业务导入其 Web DTO 并增加中央 switch。

关键保证：

- 接受请求、创建任务和必要业务占位在可控事务中完成。
- Worker 使用可信任务归属，不信任模型返回的 userId。
- 任务租约与结果提交有版本/执行代次约束，旧 Worker 不能覆盖新结果。
- 重试是幂等或显式人工确认的，不宣称外部调用天然 exactly-once。
- 涉及上游费用或执行副作用的不确定状态，需要对账或结果核验，不盲重放。
- 通知是结果的投影；通知成功不等于业务成功，已读不等于完成。

优先使用应用内调用和现有数据库事务。只有确有跨事务可靠交付需要时，采用持久化事件/outbox 与消费者幂等；不把普通方法调用全部事件化，也不为未来提前部署 Kafka。

## 10. 前端与客户端架构

分四类状态：

1. 服务器事实：消息、作业、提案、业务实体；重新打开可恢复。
2. 用户偏好：语言、侧栏固定项等，按账号同步，版本检查防覆盖。
3. 本机状态：窗口尺寸、连接服务器、草稿缓存；说明设备范围和服务端同步边界。
4. 临时界面状态：弹层、悬停、动画；不能承担业务完成判断。

按页面、业务功能和基础组件分层；聊天页拆出运行协调、消息时间线、输入草稿、提案与引用等职责。先复用现有请求和缓存能力，再选择是否需要新状态库，不用更换前端框架解决职责问题。

导航使用稳定 destination ID；URL 只是到达方式，不再兼任用户偏好身份、权限 scope 和领域标识。路由别名覆盖旧聊天链接、日程、通知与桌面入口。

双语的界面文案与业务内容语言分开；切换界面语言不重新生成或覆盖用户材料。时间存储、时区显示、表单校验与错误摘要具有一致规则。

视觉继续遵循项目设计规范，导航层级重构不等于引入另一套风格。错误有简短摘要、可展开详情和追踪 ID，不向页面输出密钥、Cookie 或原始供应商响应头。

桌面继续作为可信服务器的轻客户端。业务前后端发布与安装包更新分开：服务器界面变更通常不要求客户端重新安装；原生桥、协议或运行时变更才需要协调客户端版本。

客户端与服务器协商可用能力，旧桥缺失可降级，关键协议不兼容明确提示。服务不可达显示连接诊断；不得将后端 Key 放入安装包或为修复打开任意 IPC/导航权限。

## 11. 数据治理、授权与备份

每个资源需要稳定 ID、所有者、创建/更新时间，必要时有版本。业务状态只由所属领域转换，查询投影可以重建；原始事实、历史尝试和确认记录不可用缓存替代。

跨资源关联同时校验用户与业务父子关系。管理员可管理系统配置与账号，不因此获得其他用户的简历、消息或面试正文。

删除要列出作用范围、关联对象、派生文件/索引与保留政策；不因移动目录而扩大级联删除。是否使用软删除及恢复窗口逐类决定，不做所有表统一 deletedAt 的机械改造。审计保留操作类型、身份和必要结果，不长期复制整份敏感正文。

自托管备份必须覆盖数据库、文件及必要的加密密钥管理；只备份表却丢失解密能力并不能恢复。上线前做恢复演练，并给出结果，而不是只看到备份文件存在。

未来公开分享、团队或同步引入新的授权主体时，再显式设计共享规则与迁移。当前 userId 边界不能被“以后可能有 workspace”偷换为默认跨用户访问。

## 12. 运行部署、额度与安全边界

当前形态：Web/桌面连接前端，前端访问后端，后端使用 PostgreSQL、Redis、文件存储及外部模型/语音服务。保留本地自托管和未来托管使用同一套领域逻辑，通过部署配置区分环境。

扩展顺序：先测量瓶颈，再调整资源/索引/并发；需要时把可恢复 Worker 运行到独立进程，随后再评估多副本。不把进程内锁、定时器或本机磁盘默认为多副本可共享。

语音连接、文件大小、AI 并发、用户额度与上游费用分别限制。已存在的 usage 机制需要纳入任务与模型调用的关联：预留、结算、失败释放和重试口径清楚，不在每个 Controller 各写一套计费判断。支付订阅尚未实现的部分不在本轮顺带建设。

所有外部 Base URL、重定向及下载地址遵守出站地址策略。代码执行若开放不可信用户代码，必须先有独立进程/沙箱隔离、资源上限、网络与文件系统限制；不能因为“只是练习题”在 Web JVM 或服务器宿主机直接运行。

服务部署要能识别当前版本、健康与迁移状态。合并、构建、部署、桌面发布是四种不同结果，分别验证。Docker Desktop 的本机修复文档保留，但不能成为产品在公网运行的必要人工步骤。

## 13. 面向扩展的具体合同

以下不是要求立即创建全部接口，而是实施时必须保持的替换边界。首次出现真实第二个实现时，再抽取已验证的最小合同。

| 新需求 | 正确的扩展位置 | 必须保持不变 |
|---|---|---|
| 新增笔试、HR 面、群面等真实环节 | 面试轮次类型与领域规则 | 不新建又一个与求职并列的模块 |
| 新增另一种模拟/训练方式 | 学习域训练实现与结果摘要适配 | 不塞入万能状态表；不侵占真实面试命名 |
| 新增学习来源 | 明确来源类型、解析及归属验证 | 不让同一 discriminator 的 ID 猜多个表 |
| 新模型或服务商 | 模型能力适配、映射与合同测试 | 业务 Service 不写供应商分支 |
| 新上传格式或资料来源 | 存储/解析/来源适配 | 用户隔离、文件校验、来源追踪不变 |
| 新的慢任务类型 | 领域 Handler 与任务展示合同 | 不修改通用内核的每个中央分支 |
| 新客户端或移动界面 | API 合同和能力协商 | 授权与业务校验仍在服务端 |
| 团队共享、公开分享 | 新的授权与共享模型，单独提案 | 不把现有个人数据默认公开 |

配置只用于稳定差异；不是所有领域规则都配置化。确有复用的流程才抽象，不把“面向未来”解释成从第一天构造低代码平台。

## 14. 观测与测试：让问题可解释

一次操作能够沿 requestId、conversationId、runId、toolCallId、jobId 与业务资源关联；按需记录这些关系，不把所有 ID 强制塞到所有表。

至少能回答：消息有没有保存、任务有没有接受、正在等谁、上游何时开始输出、工具是否执行、写入是否成功、用户是否确认、是否重试或重复计费。日志默认不保存完整提示词、简历和密钥。

测试分层：

- 领域规则：状态转换、评分规则、安排、删除范围。
- 合同：模型适配、工具输入输出、异步 Handler、客户端能力。
- 集成：真实数据库迁移、用户/父子资源隔离、事务与幂等。
- 恢复：断流、重复请求、取消与引导竞态、租约过期、Worker 重启。
- 产品主线：真实面试记录 → 缺口 → 学习/重答 → 复习 → 查看进度。
- 架构约束：禁止跨域 Repository 访问、领域依赖 Web DTO、供应商类型扩散到业务层。

每次迁移必须有可观测的验收结果；“文件变少了”“换了包名”不是重构成功标准。

## 15. 迁移路线：先建立合同，再替换内部

| 阶段 | 核心交付 | 放行标准 | 回退边界 |
|---|---|---|---|
| A 基线与决策 | 术语表、现有资源/状态/权限/路由清单、主流程测试 | 全部现有模块有归属；关键历史数据与兼容合同已盘点 | 不改运行语义 |
| B 产品主线 | 求职/学习层级、统一命名、evidence 归并、稳定导航 ID | 新旧入口到达同一资源，旧侧栏偏好保留 | 可恢复旧导航；数据库不变 |
| C 数据语义 | 流程/轮次/记录关系、来源消歧、版本与尝试历史的必要补齐 | 回填异常可报告，用户/父子归属测试及升级演练通过 | 增量 schema 与兼容读取；不依赖破坏性降级 |
| D 应用边界 | 手动/Agent 复用服务、跨域来源接口、任务 Handler、资料合同 | 新实现不复制业务规则，旧新路径共用真相源 | 切回兼容适配，不建立长期双写 |
| E 执行与客户端 | 消息/运行/结果合同、引导/取消、模型能力与错误分类、能力协商 | 并发/恢复测试通过；旧客户端有明确降级路径 | 按能力开关回退；保留已写消息与结果 |
| F 整理与扩展验收 | 清理旧适配、更新正式架构文档、架构测试 | 添加一种真实扩展不再全局改中央分支；恢复和主线验收通过 | 只在兼容期限与数据核验后移除旧路径 |

这些是依赖顺序，不要求所有可靠性修复等到 E。若发现消息丢失、越权、不可恢复任务等问题，应先独立修复，再继续结构迁移。

按可验收能力拆 PR，不按“前端一次、后端一次、迁移最后一次”拆成长期不可用的半成品。8–12 个 PR 可作为初始粒度参考，但整体范围扩大后应重估；没有历史数据和恢复演练前，不承诺具体工期。

已执行 Flyway 文件不改。采用新增字段/关系 → 兼容读取 → 回填与异常报告 → 切换写入 → 验证 → 最后收紧约束的路径。跨版本旧 Worker、旧来源、旧桌面需要在实施清单里明确覆盖。

## 16. 必须避免的架构雷区

1. 只折叠菜单，仍按旧页面堆中央 Service 与工具。
2. 一次全库改名，旧 URL、工具 scope、日程链接和任务结果一起失效。
3. 用“求职大模块”替换多个小模块，却建出一个更大的万能 Service。
4. 用一张通用实体/来源/训练表隐藏不同业务语义。
5. 让 LLM 判断身份、授权或操作是否已经成功。
6. 用缓存、通知或聊天文字冒充持久化业务事实。
7. 自动重试无幂等的副作用，或把停止误认为回滚。
8. 预建微服务、消息总线、团队租户和插件平台，增加现阶段无法验证的复杂度。
9. 为兼容维护两套独立写逻辑，长期双写却没有对账与退出期限。
10. 把历史数据迁移、备份恢复、客户端兼容和运维当作重构收尾的小事。

## 17. 总体验收场景

- 今天投递 40 份，只记一个数字；不制造 40 条虚假岗位记录。
- 一个岗位两轮真实面试，多份来源准确归档；模拟训练不冒充真实轮次。
- 同一道弱题可关联学习、重答与记忆卡，能够追溯来源和评价版本。
- 没有真实面试也能自主学习、模拟训练和复习。
- 发出“删除 1、2、3 后重建”，再追加“2 不用重建”，两条消息都保留；已完成副作用如实报告，未执行部分受新要求约束，删除有明确确认。
- 断网、刷新、重启或重复请求后不吞消息、不重复写入、不复活旧确认，答案草稿与历史结果不丢失。
- 换界面语言、浏览器/桌面或旧链接进入，业务事实、用户偏好和授权仍然正确。
- 用户 A 不能关联或读取 B 的资源；同一用户也不能把流程 A 的轮次误挂到流程 B。
- 新增一种训练、新服务商或资料来源时，业务规则和通用任务内核不需要连锁修改。
- 数据库与文件能从备份恢复；桌面版本、服务版本和任务版本不一致时有明确兼容行为。

## 18. 待决策与实施前核验

本方案建议批准的方向：两条业务主线、真实面试拿回 Interview、evidence 归入进度视图、保持模块化单体、渐进迁移。

实施前还需要以实际数据和合同核验：轮次与记录的历史分布、RECAP 来源可解析情况、旧客户端范围、当前授权策略与用户设置、删除关联行为、任务持久化/重试细节、备份恢复是否真实可用。没有核验的部分不能在 PR 中宣称已解决。

后续由用户设定原生 Goal 时，建议以本方案某一阶段的可验收成果为目标，而不是“把整个未来架构一次做完”。每阶段结果应包括代码、升级路径、测试证据、未完成项及正式文档同步。
