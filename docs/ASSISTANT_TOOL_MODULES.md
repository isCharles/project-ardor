# 助手工具模块与统一执行边界

## 当前实施范围

简历的五个既有工具使用 `ResumeAgentToolProvider`：`list_resumes/analyze_resume/get_resume_analysis_status/get_resume_analysis/delete_resume`。资料应用服务输出不含存储键/解析正文的 `ResumeView`，并复用不可变 `ResumeAnalysisSnapshot`；首份/最新分析选择与分数截断在资料域完成。HTTP 元数据十一字段、报告六字段，工具列表七字段、分析四字段不变；队列仍负责任务状态。上下文引用和学习删除目标改用既有应用视图，不恢复实体读取。模块不调用删除业务方法，提案仍由宿主记录并交用户确认。

本批将显式分析 ID 与简历父 ID 的一致性校验移入资料应用服务，HTTP、其他应用调用均不能跳过；用户归属仍由原 Service/Repository 联合限定。上传包装复用原解析和两次 flush，快照在生命周期时间戳生成后返回；不改评分、源文本、文件路径或任务执行器。无 migration，回退应用即可。

日历建议的三个既有工具使用 `CalendarAdviceAgentToolProvider`，不再由中央类实现。`CalendarAdviceService` 返回不可变的 `CalendarAdviceView`，HTTP 将其映射为原五字段响应；用户归属、旧文本读取、规范化和清除规则不变。删除建议卡仍仅生成用户限定单例的确认提案（`/api/calendar/advice`），不调用删除 Service，也不扩大为删除日程。

工具适配器不再导入任何业务 HTTP DTO。简历分析任务直接使用队列既有七字段应用结果；纪要任务由 `InterviewRecordTaskView` 统一保留十字段兼容投影及旧/最终纪要链接，HTTP 复用同一投影。没有新增任务状态、表或 Worker。此项不表示所有跨域实体读取或中央工具分支已经拆除。

自动化的五个既有工具现使用 `AutomationAgentToolProvider`：`list_automations/get_automation/create_automation/update_automation/delete_automation`。手动 HTTP 与 Agent 都读取 `AutomationService` 生成的 `AutomationView`，不再由中央工具类导入 HTTP 响应或持有自动化实体。快照保留原 12 个 JSON 字段和 null 语义；创建/更新在事务内 flush 后生成，保留生命周期时间戳；查询不 flush。调度器仍在自动化自身边界使用实体，不将它跨域输出。

这批选用现有提供者机制和具名快照，而不是新建自动化注册中心、平行权限表或通用任务实体。`AutomationService` 的快照入口委托原有校验/调度规则，HTTP 仍负责请求校验及状态码，自动化调度、claim 和历史状态不改变。无新增 migration；回退应用代码即可，既有自动化和对话数据保留。

知识资料的四个工具已从 `CareerAgentTools.BoundCareerTools` 移入助手域的 `KnowledgeAgentToolProvider`：`list_knowledge_documents`、`search_knowledge`、`research_knowledge_from_web`、`delete_knowledge_document`。

模块仍调用资料域 `KnowledgeService` 的应用快照接口，不拥有知识实体、仓储、索引或删除事务。工具名、参数名、scope、HTTP 路径和结果含义保持兼容。本批无 schema 迁移，也不改变用户权限设置。这是进程内适配器拆分，不是插件平台：不加载用户上传代码，不允许模型登记工具，也不新增独立服务。

## 装配与生命周期

Spring 发现 `AgentToolProvider` 组件并交给宿主；已有直接构造入口默认装配知识、自动化、日历建议与简历模块，供旧测试和调用方兼容。每次 `bind` 都创建新的绑定对象，`AgentToolContext` 捕获本轮可信用户及宿主的提案、不可信内容包装回调，不通过模型参数选择用户。

`AgentToolBundle` 只提供不可变的绑定对象列表。普通对话、流式对话及自动化继续经过 `ApprovedAgentTools`，不直接将提供者暴露给模型框架执行。连接测试使用同一发现入口收集 schema，但工具执行器仍为原有 no-op，不产生业务副作用。

重复工具名在执行装配时拒绝，不以发现顺序覆盖已有工具。扩展提供者不能绕过能力目录；新增工具仍须登记现有 `ToolCatalog`，并按需要补齐明确意图、权限与业务服务校验。局部适配器避免中央类继续增加工具方法，不意味着取消中央安全策略。

## 必须保留的执行合同

开发者轨迹的工具 Schema 也从提供者的 `toolTypes()` 发现，不得恢复只扫描中央类。提供者返回模型实际暴露的绑定类，不需要绑定用户或执行 Service；`AgentToolSchemaCatalog` 复用 LangChain4j 的 `ToolSpecifications` 和固定版本 JSON Schema 转换，保留可选参数、数组子项和枚举。此调用不代表工具授权；权限仍由运行时执行合同决定。升级 LangChain4j 时应运行 Schema 合同测试，核验内部转换辅助方法的兼容性。

1. 写入授权继续由**宿主绑定的可信请求**控制，而不是由被拆出的工具对象自行声明。`ToolIntentScope` 的判断对象仍是根绑定对象。
2. 全部模块共用同一轮的重复写入防护、审批、运行 lease、取消、计时、追踪与执行审计。不得按模块另建尝试缓存而允许重复副作用。
3. 资料检索及网页收录结果继续使用 `untrusted_external_content` 包装；材料中的命令不能授权写入。
4. 删除工具先通过用户限定的应用服务读取真实目标，再调用宿主提案回调。查不到目标不得生成确认卡；工具不调用删除业务方法。最终删除仍由用户界面确认后的受鉴权 HTTP 接口执行。
5. 提案留在宿主本轮的待确认列表，保留现有结构化审计与恢复身份，不因对象拆分改成模块私有列表。
