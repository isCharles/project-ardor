# 面经 → 补强 → 复测：验收路线

这份清单用于验收一次真实的求职复盘闭环。页面文案可能随语言设置切换；以下路径比按钮措辞更稳定。演示请使用虚构面试材料，不把真实简历、面经或 API Key 写进测试记录。

## 人工演示（需要可用的 Ardor 服务和模型）

1. 登录后在 `/app/recaps` 提交至少 30 字的面试记录，包含可核实的日期、公司、岗位、问题与自己的回答。提交后应返回对话工作台，后台整理状态可见；无需在上传页等待模型完成。失败时应有原任务的重试入口，而不是要求重新粘贴全文。
2. 后台任务完成后再进 `/app/recaps`。列表应出现这份面经；点击后应看到结构化的逐题报告、真实材料支持的优势和薄弱点，而不是原始 JSON。若日期、公司或岗位未被识别，手动补全并刷新，确认保存。不要把模型推测当作真实面试信息。
3. 打开 `/app/evidence`，在薄弱题轨迹中选择“重新回答”。`/app/replay?question=...` 应保留原问题与当时回答，提交新回答后呈现对比反馈；再次打开同题仍能看到历次回放。手动安排一次未来日期的变式复测，日历里应只出现一项可跳转的复测待办。
4. 从成长证据页为这道薄弱题制定学习计划，或在 `/app/learning` 手动创建。若由 Agent 提议，应先在对话里看到待确认卡片：**确认之前**计划和日历都不应新增；确认后仅创建一次，刷新对话也不能重复创建。删除已确认计划后，旧卡片不能重新生成它。
5. 打开学习计划，完成一轮练习。反馈应保留本轮题目、自己的答案与逐题解释；不达标时进入新的复习轮次并更新日历，达标后标记完成。连续点两次提交不能让旧一轮评分覆盖新一轮；系统应提示刷新。
6. 从日历进入复测，回答此前安排的变式问题。提交成功后，回放记录与日历完成状态应同时出现。若在模型返回前取消该复测，系统不能留下孤立的回放记录。

## 自动验收的边界

`.github/workflows/golden-path-acceptance.yml` 在一次性 PostgreSQL、Redis 和假模型服务中运行 `backend/src/test/resources/golden-path-acceptance.mjs`。它已覆盖异步面经整理、弱题回放、学习复练、日历联动、跨用户读取与写入拒绝（包括学习计划和关联日历任务）、Agent 计划确认、失败任务重试、取消中的复测回滚以及并发学习评分。假模型有意返回固定数据和可控故障，所以该检查**不证明**真实模型质量、外部网络、浏览器页面观感或本机 Docker 正常。

手动触发同一工作流时，还会启动一次性前端并用 Chromium 运行 `frontend/tests/golden-path-ui.mjs`：检查登录、删除后的 Agent 学习建议在刷新后仍显示为已移除、另一条待确认建议须由用户点击才创建且刷新后不重复、两轮练习的反馈与历史记录及日历完成状态、面经报告；另用隔离账号检查失败面经的页面重试和用户间列表隔离、弱题重答遇到模型故障后答案跨页面保留且重试只生成一条记录、从日历进入变式复测并完成、上海时区缺失日期与公司岗位的逐项补全。浏览器检查覆盖这些合成数据路径的页面行为，但仍不证明真实模型质量或所有页面的视觉效果。

`backend/src/test/resources/golden-path-acceptance.mjs` 会创建用户与记录，且要求 `ARDOR_ACCEPTANCE_DISPOSABLE_DB=true`；**只可在可丢弃的隔离数据库运行，严禁指向日常或生产数据库**。前端 PR 另由 `.github/workflows/frontend-quality.yml` 执行干净安装、Next 类型生成、类型检查、lint 与正式构建；这也不是浏览器端到端验收。

本机 Docker 当前是否可用必须以实时 `docker info` 和端口/健康检查为准。2026-10-10 的安全启动脚本失败记录见 `docs/DOCKER_DESKTOP_SOCKET_RECOVERY.md`。2026-10-11 本机只重建并更新了前后端：后端 163 个测试通过；四个容器运行，后端、PostgreSQL、Redis 健康，`pg_isready` 接受连接、Redis 返回 `PONG`；前端 `/` 为 200、后端匿名 `/` 为预期 401，Flyway 最新版本 31 成功。此项仅证明本机服务运行，**不等于**已用真实模型完成上述人工演示。
