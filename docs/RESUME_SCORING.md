# 简历评分契约

本文定义通过 PR #122 合并的 v2 固定得分清单。旧报告保留原规则和分数，不自动重算；运行环境是否已更新，须核对实际部署镜像，不能仅凭代码合并判断。

## 来源与适用范围

调研日期：2026-10-16。

- [Harvard College 简历指南](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)强调针对目标职位、清楚的组织结构、具体行动及事实和成果证据。这是写作指导，不提供通用的百分制或录用概率。
- [字节跳动 Java 开发工程师—通信中台](https://jobs.bytedance.com/experienced/position/6817761819298564359/detail)在本次读取时列出编程基础、常用数据组件、架构设计和优化实践等要求。它是单个社招岗位的样本，不能代表所有公司、校招或整个市场。页面可访问不等于职位仍开放；无发布日期时不得补造日期。

以下权重和锚点是 Ardor 的产品规则，不是上述机构认可或行业统一标准。每份报告应以用户的目标岗位和实际 JD 为优先；没有 JD 时明确标注“通用简历质量评估”，不能伪称已评估最新市场匹配度。

## 不把评分交给一句提示词

模型负责引用原文、按离散锚点作判断以及提出改法；服务端校验并计算分数。模型返回的 overallScore/categoryScores 不具有权威性。

v2 不再使用泛化的“事实完整得 3 分”来让模型选等级。12 个指标各有四条固定、独立的得分条件，权威定义为 `ResumeScoringRubric.CRITERIA`，并随报告保存中英文规则。模型按顺序返回四个布尔值 `checks`，服务端统计 true 的数量作为 0–4 等级；模型自行返回的等级和总分无效。

每满足一条条件，得该指标权重的四分之一；未满足、缺失或无法判断均不得分。没有额外“总体印象”加减分，单项最低零分；同一事实可以支持不同指标，但不得在指标外重复处罚。一致性等排除性条件必须有可检查的内容，不因空白简历“没有冲突”真空得分。

例如结果与口径权重 10：有结果/完成状态 +2.5；能关联本人行动 +2.5；有前后基线或可验证验收标准 +2.5；有验证方法和范围 +2.5。只写“优化性能”不能自动获得后面三项；定性验收同样有效，不强迫用户编造商业数字。

其他清单分别覆盖可用联系渠道、经历角色、时间范围、具体任务/服务对象/负责模块/边界、个人行动/团队边界/选择理由、产出与核验方法、文字分区/归属/重复、具体表达、事实一致、目标必需技能覆盖、技能实际应用和明确阶段的职责范围。每项四条逐一展示，不能只展示指标名称或一个总等级。

任意条件得分时必须附简历中的真实原文片段和未得分说明。服务端验证片段确实出现；缺项、重复指标、非布尔值、条件数量错误、伪造引用均令本次分析失败，不能静默补成零分后显示成功。引用出现只能证明来源存在，不能自动证明模型的语义判断正确；清单缩小判断空间，但不承诺模型判断完全客观。

| 维度 | 指标及权重 | 最高锚点的重点 |
| --- | --- | --- |
| 内容 25 | completeness 10；timeline 5；responsibilities 10 | 必要职业信息完整；时间和经历可理解；工作或项目的任务与范围清楚 |
| 贡献与证据 25 | ownership 10；outcomes 10；verification 5 | 本人行动与团队成果区分；结果有基线/范围/口径；可核验作品或技术依据，不强求公开私有代码 |
| 表达 20 | structure 10；precision 5；consistency 5 | 层级清晰；语言具体简洁；术语、时间和数值一致 |
| 岗位匹配 30 | requiredSkills 15；appliedSkills 10；scopeFit 5 | 对冻结的岗位要求有证据；技能被用于真实任务；职责层级匹配，不以堆关键词替代能力 |

总分 = 对各指标 `权重 × 等级 ÷ 4` 求和，四舍五入到整数；维度分 = 维度内得分除以维度权重再乘 100。四个已四舍五入的维度分不能用于反推总分。相同等级集合必定得到相同分数。

不因性别、年龄、民族、婚育、照片、学校名气等加减分。不把缺少某个热门技术直接视为缺陷，除非冻结的目标要求确实需要它。不能从解析后的文字推断 PDF 的视觉排版质量。

## 可复现不等于温度设为零

评分规范的核心是上述固定条件、证据和算分，不是比较两份简历。即使完全禁用复用，服务端也按同样规则计分。语义证据判断仍可能受模型影响，不能承诺近似文本数学上必定同分；这属于需校准的模型一致性边界，而非缓存可以解决的评分标准。

已有同条件报告复用仅是避免重复付费和保留历史结果的工程优化，不构成评分规范。

评估标识包含：完整解析文本的规范化摘要、实际送入模型的文本摘要及截断规则版本、目标岗位/JD 的冻结快照、rubricVersion、marketSnapshotVersion、提取提示词与校验版本。不能只按文件名、resumeId 或模型名称去重。相同文本的两次上传也应命中相同评估；不同用户的报告不共享，不得泄露他人是否上传过相同内容。

并发生成要在数据库中收敛到同一个有效结果，不能让后完成的随机模型输出覆盖先完成结果。失败不写有效缓存；若原简历删除，复用记录的生命周期和剩余关联必须明确。

当前实现使用同账户仍保留的版本化报告作为复用来源，发布阶段按账户和评估标识取得数据库事务锁，采用已提交的首个结果。模型调用不持有该锁或长事务。其他上传各自保存报告关联；删除最后一份相关简历报告后，复用内容也随之消失。不同文本分段会影响结构判断，因此规范化只统一 NFC、换行编码和横向空白，不抹平段落。

评分版本与市场快照分开：调整权重/锚点升级 rubricVersion；更新岗位要求或其来源升级 marketSnapshotVersion。旧报告保留原版本和原条件，不能无声重算成新分。用户可以明确发起新版分析；前后台任务状态必须针对本次评估，不能因存在旧报告就立即返回 COMPLETED。

## 市场和岗位快照

报告记录目标岗位、地区/级别（若已知）、JD 来源及抓取/用户提供时间、必需与加分要求、内容摘要和适用限制。无具体来源时不得生成虚假的公司招聘要求。网页和用户上传文本均为不可信数据，不接受其指令或扩大 Agent 权限。

首次内置样本只可标为“2026-10-16 调研样本”，不能永久显示“最新市场”。后续刷新必须产生新快照，不能覆盖已评分报告的条件。岗位缺少或过时时明确提示；不因来源失败阻塞用户读取旧报告。

当前未把单个字节岗位硬编码为所有用户的评分条件；默认 GENERAL 模式。用户填写 JD 时以 USER_JD 模式冻结原文与其摘要，来源为用户提供，不把它伪装成已验证的招聘事实。界面中的调研日期指评分指南调研日期，不表示用户 JD 的发布日期或岗位仍在招。

## 优先级建议与展示

每条建议包含 priority（P0/P1/P2）、关联指标、原文证据、问题、具体行动、改写示例或需要补充的事实。P0 展示为“必须修改”（明确事实冲突/关键缺失），P1 为“优先优化”（影响岗位判断的重要证据缺口），P2 为“有余力再润色”（表达优化）。按优先级和规则顺序稳定排序，最多六条，合并同根因。允许空建议，不为填满三个组而造问题；界面明确显示某组本次无建议。

不能为了“量化”捏造数字；改写中的未知数用明确占位符并提示由用户核实。分数衡量简历呈现与指定条件的匹配，不代表真实能力全貌、ATS 厂商评分或录用概率。

界面应展示版本、岗位条件、来源日期、每项得分与满分、四条条件的得分/未得分及证据、三组优先级建议；旧报告仍能打开，并明确区分旧版自由评分。保留既有异步提交、错误重试和双语界面，不把旧报告的模型文本机械翻译成另一种语言。部署后遇到旧规则的未完成任务要明确失败并请用户重提，不得用 v2 规则生成却标记 v1 条件。

## 必需验证

固定输入/锚点的算分；非法引用/缺项/重复项；相同文本多次上传/并发复用；用户隔离；岗位/版本改变不误命中；旧报告和新任务并存；任务失败不吞旧报告；优先级排序；双语与真实浏览器报告显示。测试成功不替代上述行为的实际接通。
