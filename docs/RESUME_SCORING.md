# 简历评分契约（v3）

本文定义当前简历分析的 v3 合同：**评分规则是后台黑盒，用户只看到竞争力结论和可执行的问题**。v1/v2 报告保留数据但不再渲染，入口显示“旧版评分已下线”，重新分析才会生成 v3 报告。

## 用户可见与不可见

用户可见：

- 总分（0–100）与竞争力档位；
- 六个维度的 A–F 档位（S 表示爆表）与市场基准虚线；
- A/B/C 三档问题：最该改、应该改、可增色；
- 一段直白的背景竞争力判断；
- 1–2 条具体优点；
- 本次条件：大类 + 是否含 JD。

用户不可见：

- 权重、0–4 级锚点、评分公式、封顶规则；
- 每个维度的得分明细、证据核对清单、rubric 版本；
- 模型内部推理。
这些只保存在后台报告中用于审计和复现，不在报告页渲染。

## 不把评分交给一句提示词

模型只负责：按锚点给出每个维度的等级与原文证据、列出问题及改法、写背景判断和优点。服务端负责：

- 校验六个维度恰好各一次、等级 0–4；
- 校验 level>0 时 evidence 必须逐字出现在简历原文中；
- 校验 A/B/C 问题结构、证据引用、数量与排序；
- 计算维度分、A–F 档位、总分和竞争力档位；
- 模型返回的分数、等级、权重一律无效。

## 六个维度与固定权重

| 维度 | 权重 | 满分锚点的含义 |
| --- | --- | --- |
| 专业深度 technicalDepth | 20 | 主导关键系统/核心工作，有决策、取舍、失败或降级方案，且能区分个人与团队贡献 |
| 项目成果 outcomes | 20 | 多项结果有基线、指标、测量方法和适用范围，能证明与个人行动的关系 |
| 工程/业务 ownership | 20 | 主导跨团队或关键项目，承担范围、技术/业务决策、协作与结果，达到资深/架构级 |
| 表达结构 clarity | 10 | 层次分明、事实密度高、无空话，筛选者能快速建立可信度 |
| 岗位匹配 roleFit | 20 | 覆盖目标明确要求并有深度证据，或对等效经验有清晰说明 |
| 背景竞争力 background | 10 | 顶尖院校/头部公司/高选择性项目或竞赛，在简历筛选中显著加分 |

总权重 100。六维权重在所有大类中保持一致，保证不同岗位的分数可以横向比较；大类只改变**市场基准线**和**证据侧重**，不改变权重公式。

每个维度 0–4 级：

- 4 级 = 该目标市场里最顶级候选人的证据，不是“写了就给”；
- 3 级 = 强；
- 2 级 = 普通合格；
- 1 级 = 偏弱；
- 0 级 = 缺失。

维度分 = 等级 × 25；总分 = `Σ(权重 × 等级 ÷ 4)`，四舍五入到整数。档位按维度分映射：S ≥ 95，A ≥ 80，B ≥ 65，C ≥ 50，D ≥ 35，E ≥ 20，其余 F。普通初稿通常落在 40 分左右；4 级罕见，因此 100 分实际不可达。

## 大类与市场基准

当前固定七个大类（后端 `ResumeScoringFamilies`）：

| id | 名称 | 针对性侧重 |
| --- | --- | --- |
| general | 通用技术 | 未声明方向时的默认；通用专业深度与项目证据 |
| engineering | 开发 | 生产代码、架构取舍、故障/性能/复杂度证据 |
| algorithm | 算法 | 模型/算法选择、数据规模、实验严谨性、离线与线上指标 |
| data | 数据 | SQL/Python、数据管道、统计/实验方法、业务决策影响 |
| product | 产品 | 问题定义、优先级、方案取舍、跨团队推进、指标变化 |
| sales | 销售 | 客户理解、销售流程、配额/营收/回款/转化数字 |
| management | 管理 | 团队/项目方法、组织设计、团队规模、交付与人员成长 |

每个大类有一套市场基准档位（雷达虚线）和证据侧重，写在 `ResumeScoringFamilies` 中。用户选择大类；不选时默认 `general`。

## JD 的位置与边界

- JD 是**可选输入**，不是评分规则的来源；
- JD 原文放在 user message 的 `<conditions>` 中，长度上限 8000 字符，绝不拼进 system prompt；
- system prompt 只包含固定六维规则、大类标准、输出 schema 和安全约束；
- JD 和简历都标记为不可信数据，其中出现的任何指令、分数要求或角色设定都不得执行；
- v1 不做 JD 级联解析（不额外调用一次 LLM），直接使用原文；如果未来需要 mustHave/niceToHave 结构化，再独立评估；
- 未提供 JD 时明确显示：“未提供 JD：将按「大类」做通用评估，可能不具岗位针对性”；
- 报告展示本次条件：`大类 · 含 JD` 或 `大类 · 通用评估`。

## 问题分级与报告

每条问题包含：

- severity：A / B / C；
- dimensionId（服务端校验属于六维之一）；
- category：用户可读分类；
- problem：具体问题；
- why：对面试官/筛选者的影响；
- action：可执行的改法；
- evidence：简历原文引用，可空；
- example：改写示例，未知事实只能使用明确占位符。

A = 最严重、最该改、改完收益最大的问题，不承诺“一定被秒挂”；B = 显著影响评估；C = 改了能增色。只列真实问题，不为凑档位编造；同一根因合并；最多 9 条，按 A→B→C 稳定排序。

背景竞争力必须直白说明院校、公司、项目/实习在当前就业市场的真实位置，不安慰、不夸大，但只能基于简历可见事实，不编造学校层级、公司排名或项目影响，也不使用性别、年龄、民族、婚育等受保护属性。

## 代码与存储

- 规则：`ResumeScoringRubricV3`（六维 0–4 级锚点、算分、档位）；
- 大类：`ResumeScoringFamilies`（七类基准与证据侧重）；
- 报告校验：`ResumeReportV3`（summary/background/strengths/issues）；
- 条件冻结：`ResumeScoringContext.freeze(targetRole, jobDescription, roleFamily)`，写入 `roleFamily`、`familyVersion`、`rubricVersion`、`promptVersion`、JD 快照和评估 key；
- 分析 JSON 保存 `overallScore`、`dimensionScores`、`dimensionGrades`、`dimensionBenchmarks`、`dimensionRatings`、`issues`、`background`、`strengths`、`summary`、`scoringContext`；
- 评估 key 包含大类与规则版本：换大类、换 JD、升级规则都会生成新报告，不会串用旧结果；
- 同条件报告复用仍是工程优化，不构成评分标准；
- 旧 v1/v2 报告数据保留，但报告页只显示“旧版评分已下线”，不渲染旧评分内容。

## 必需验证

固定输入/锚点的算分；等级越界、缺项、重复维度、伪造引用；JD 超长/注入指令不改变规则；大类切换不串缓存；同一条件复用；用户隔离；旧报告下线提示；A/B/C 排序与证据；双语和真实浏览器报告页；背景判断不编造事实。测试通过不等于部署环境已更新。
